画一张 Mermaid 图，主题：${@:-当前对话里正在讨论的任务}。

## 总目标

图自己就要让人看懂，不依赖图外解释：用户只看图，也能明白整体结构、数据怎么流、哪里容易出问题。任何想写在图外的话，都应该想办法写进图里（唯一例外是交付时的导航性导读，见「交付」一节）。

## 第〇步：先判断画哪种图式，再动笔

用户的问题分两类，画法完全不同。判断不了就先用一句话问清。

**机制图：用户想理解一个系统怎么运作时，默认画这种。**

- 典型问法：「XX 是怎么实现的」「整体架构是什么」「事件驱动是怎么跑的」「并发模型是什么」「帮我梳理一下这个东西」。
- 回答的问题：这是什么模式？谁跟谁通过什么通道通信？控制流和数据流往哪走？
- 画法核心：**用形状表达结构，禁止把一切画成从头到尾的线性流程图。**
  - 线程 / 进程 / 模块边界 → `subgraph` 框起来，框上写名字。
  - 队列 / 管道 / 缓冲 → 圆柱节点 `A[("事件队列")]`，标清谁写入、谁读出。
  - 事件循环 / 常驻循环 → 画成圈：节点加自环边，如 `循环[("事件循环")] -->|"取下一个任务"| 循环`，圈旁边挂上它消费的队列。不要画成直线。
  - 生产者消费者 → 生产者一侧、通道居中、消费者一侧，箭头标方向，标清"谁在什么时候唤醒谁"。
  - 一次性启动流程 → 这才用普通箭头直线连。
- 全景图硬限制：**不超过 9 个节点，每个节点不超过 2 行文字**。判断条件、阈值、字段名、表名一律不进全景图，全部下沉到子图。
- 例：用户问"事件驱动怎么实现的"，正确画法是一个圈（事件循环）加两个圆柱（微任务队列、宏任务队列）和几条进出箭头；错误画法是十几个节点从"脚本开始"一路连到"脚本结束"。

**流程图：用户要看一件事情一步一步怎么走时才画。**

- 典型问法：「这个任务怎么跑的」「帮我梳理这个流程的步骤」，或已经钻取到最深层、要看具体执行顺序。
- 画法规则：
  - 按代码真实的执行顺序画，一条主线，支线折叠或省略。不超过 12 个节点。
  - 判断节点用「判断：」或「检查：」开头，把代码真正判断的条件写完整，有阈值直接写数字。
  - 模式切换（正常模式 / 补漏模式 / fallback）先写清"为什么会进入这个模式"，再写这个模式做什么，只贴模式名不算写清。
  - 表与数据流规则（见下文）在这一类图里生效。

## 第一步：分层钻取，默认只画一层

- 第一张永远是全景图：只有角色（谁）、通道（通过什么）、方向（往哪流）。细节全部下沉，不画。
- 交付时在回复末尾列「可深入」菜单：全景图里值得展开的部件，每项一行编号，如「可深入：① EventStream 管道怎么唤醒消费者 ② Agent.processEvents 怎么维护状态」。
- 用户点名某个编号，才画那张子图，图标题写明「展开自全景图的②」。子图里才允许出现该部件的字段名、具体条件、内部判断。
- 一次只展开一层。用户没连着点名，就不要一口气把所有层全画完。
- 流程图过密时，先想是不是该回到全景图分层，而不是拆成 2~3 张一样密的图。确属同一层的连续阶段才拆，每张标注「图N/M：XX阶段」。

## 第二步：用词与写法（所有图通用）

### 用词

- 只用简体中文。必要的英文只保留真实表名、字段名、任务名、代码里的固定名字。
- 英文字段：先写中文意思，再在后面带英文名，如 `股票标识（stock_key）`、`锁过期时间（locked_until）`。不要硬翻成"脏的股票键"这类不自然的话。
- 代码里的状态词翻译成业务意思：`cursor` 是"上次停下来的位置"，`dirty` 是"待处理"，`bootstrap` 是"补漏模式"。
- 节点文案用白话，按正常人说话的顺序写。不用"主路 / 旁路 / 回放链路"这类图外才能懂的词；一定要用，就在节点里把意思展开写清楚。

### 边（箭头）

- 边上的文字强制用动词短语："写入待办表""唤醒消费者"。不要只写名词（"数据""状态"）。
- 边文字统一放 `|说明|` 里，不要用 `--文字-->` 的旧式写法；边文字里不要放 `*`、编号列表等容易触发解析错误的符号。

### 表与数据流（流程图和深层子图适用；机制图里数据表也画成圆柱）

- 涉及数据库时，把关键表名画进图里，并写明这张表是干什么的：队列表、待办表、锁表、缓存表必须说明用途。
- 关键步骤标明动作：读表、写表、更新表，落到哪张表。尽量写清"为什么读这张表"。
- 待办表、缓存表写清"怎么来的"：谁写入、什么时机写入。某张表专供某个后台任务，直接写任务名。

### 语法安全

- 所有节点标签用双引号包裹：`A["文本"]`、`B{"判断：xxx"}`、`C[("队列")]`。含中文括号、斜杠的内容只放引号内。
- 示例（好的机制图写法）：

```
flowchart TD
    subgraph 同一个 JS 进程
        P["生产者：runAgentLoop"] -->|"每个事件调用 emit"| Q[("事件队列")]
        Q -->|"队列有货立即交付<br/>队列空则挂起等待唤醒"| C["消费者：for await 循环"]
        C -->|"处理完取下一个"| C
    end
```

## 第三步：语法校验（必做，不通过不算画完）

1. 建本次专用的稳定目录，方便回看和对比几次钻取的图：`mkdir -p /tmp/pi-draw/$(date +%Y%m%d-%H%M%S)`。本次所有 `.mmd` 和 `.svg` 都放里面，文件名用序号加简短英文主题（如 `1-overview.mmd`、`2-eventstream.mmd`）；多张图每张单独一个文件。
2. 执行下面的命令（`$DIR` 换成第 1 步建好的目录；`-p` 指向已配好的浏览器配置文件，里面指定了本机 Chrome 并关闭沙箱，缺了它 mmdc 会崩；多张图时对每个文件各跑一次，改 `-i` 和 `-o` 的文件名）：

```bash
mmdc -i "$DIR/1-overview.mmd" -o "$DIR/1-overview.svg" -p ~/.pi/agent/mermaid-puppeteer.json --quiet
```

3. 退出码非 0 时，mermaid 的解析错误会打在输出里：读错误、修语法、重跑，直到通过。
4. 配置文件或 Chrome 不存在时，停下来告诉用户，不要自行安装。
5. 不要跳过校验直接交付，也不要只靠肉眼检查。

## 第四步：交付

- Mermaid 代码只写进 `.mmd` 文件。**回复正文里不要贴 mermaid 代码块**，用户要看源码自会打开文件。
- 回复正文只包含三样东西，全部加起来不超过 5 行，只做导航不做讲解：
  1. svg 产物路径（每张图各一行）。
  2. 每张图一句话导读：画的哪一层、对应哪个文件。
  3. 画的是全景图时，附「可深入」菜单。
- 图外的解释仍然必须想办法写进图里；上面这三样是唯一允许的图外文字，不要写"整体结论先说一句……"这类论述。
- 用户看图后指出"某个词不懂 / 某个节点不顺 / 某张表没讲清"时，直接改图内文案并重新校验。不要把解释放到图外补充来代替改进。
